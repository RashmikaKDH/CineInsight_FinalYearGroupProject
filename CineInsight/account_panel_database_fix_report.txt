1. Root Cause Analysis
================================================================================

1. Synchronous Database Lookup in Saved-Reports Listing:
   In services/report_import.py, get_user_saved_reports() was synchronously calling
   get_analyses_for_user(user_id) to look up title and analysis date metadata from MySQL.
   This meant that simply visiting /reports or /profile immediately triggered a synchronous
   database query across all user analyses.

2. Unbounded Database Socket Waits:
   Neither app.py:get_db_connection() nor services/db_service.py:_get_connection() passed
   finite timeout arguments to mysql.connector.connect().
   By default, socket connections and read operations wait indefinitely. If MySQL stalls
   (e.g., during table opening, metadata lock acquisition, or hung table locks), the Python
   thread blocks forever on the underlying socket recv() call. A try/except block does not
   protect against this because the call never returns or raises until the connection is
   severed.

3. Impact on Profile, Reports, and Login:
   - When MySQL stalled, /profile and /reports hung indefinitely while waiting for get_analyses_for_user().
   - /signin hung indefinitely while waiting for SELECT ... FROM `USER`.
   - Users and automated tests were left waiting without any response or timeout recovery.


================================================================================
2. Changes Made
================================================================================

1. Decoupled Saved-Report Listing from Database Availability:
   - Completely removed get_analyses_for_user() from services/report_import.py:get_user_saved_reports().
   - get_user_saved_reports() now reads exclusively from local report JSON metadata stored
     under imported_reports/<hashed_user_id>/.
   - Title, video_url, analysis_date, scores (positive sentiment), sarcasm rate, total segments,
     and pipeline_status are extracted directly from the stored JSON file.
   - If analysis_date is absent or empty, the file's modification timestamp (mtime) is used as fallback.
   - Missing optional fields and malformed files (syntax errors, non-dict JSON) are caught
     defensively and skipped without crashing.
   - No external YouTube or Gemini API calls are made.
   - Report files are read-only; no modifications are made to existing report files.
   - Preserves user ownership isolation, newest-first ordering (by mtime), and latest-5 limit.

2. Bounded Database Waits in Connection Factories:
   - Configured finite connection, read, and write timeouts in both:
       * app.py: get_db_connection()
       * services/db_service.py: _get_connection()
   - Configured constants with sensible defaults:
       * DB_CONNECTION_TIMEOUT = 5 seconds (overridable via env)
       * DB_READ_TIMEOUT = 10 seconds (overridable via env)
       * DB_WRITE_TIMEOUT = 10 seconds (overridable via env)
   - Preserves existing connection settings, credentials, and transaction semantics
     (start_transaction, commit, rollback).
   - No duplicate-query retry loops or background worker threads were added that could hide
     unnoticed running queries.

3. Differentiated Profile Outages from Missing Users:
   - In app.py:profile():
       * If a database error or timeout occurs (mysql.connector.Error, TimeoutError, OSError),
         db_unavailable is flagged as True. The view falls back to session identity, loads
         saved reports from local JSON metadata, and renders the profile with an accessible
         status notice: "Live account details are temporarily unavailable. Showing cached session details."
       * If the database query executes successfully without errors, but returns None, the user
         account was deleted or no longer exists. The session is cleared and the user is redirected
         to /signin. A deleted account is never silently presented as an active user.

4. Bounded Login Timeouts and Error Handling:
   - In app.py:signin():
       * Caught timeout exceptions (ConnectionTimeoutError, ReadTimeoutError, WriteTimeoutError,
         TimeoutError, and timeout message matches) specifically.
       * Returns HTTP 503 Service Unavailable with a clean user-facing error message:
         "Service temporarily unavailable. Please try again shortly."
       * Database credentials, table names, and internal exception traces are never exposed in the UI.
       * Users are NEVER authenticated through a database-error fallback; sessions remain unauthenticated.

7. Remaining Limitations and Architectural Context
================================================================================

1. Client-Side Timeouts vs. Server-Side MySQL Stalls:
   Adding connection_timeout=5, read_timeout=10, write_timeout=10 configures the MySQL client
   (Flask / Python) to abort waiting on unresponsive network sockets after a bounded duration.
   This guarantees that the web application will never hang indefinitely when MySQL queries
   stall (e.g. during "Opening tables" or lock contention).
   However, adding client timeouts DOES NOT resolve or fix the underlying server-side MySQL
   stall itself (which is typically caused by filesystem lock contention, exhausted table cache,
   or deadlocked queries on the MySQL daemon). It only bounds the application's wait time and
   allows Flask to return a controlled, user-friendly 503 response.

2. Video Title Fallback:
   Because get_user_saved_reports() no longer performs a database query or external API call,
   if a legacy report JSON file is missing an explicit title field, it displays the YouTube URL
   or fallback ID. This is an intentional design trade-off to ensure fast, deterministic,
   database-independent page loading.
